# App icon and menu bar: implementation plan

**Goal:**
- Shepit has its own icon, B2 (the cross-stitch rhombus), wherever macOS shows an app's icon.
- The menu bar shows the rhombus in every state instead of emoji.

**Architecture:**
- **The menu bar:**
  - `MenuModel.title(_:) -> String` becomes `MenuModel.icon(_:) -> MenuIcon`, a value in ShepitCore. It also says whether the icon is plain (no colour).
  - `MenuController` draws it with AppKit: a template image when plain, drawn in colour otherwise.
  - It draws only when the icon changes, as the meeting's clock refreshes the menu bar every second.
  - A debug command, `Shepit menubar-test`, shows every state in the menu bar without installing, as `panel-test` does for the call panel.
- **The icon** is an Icon Composer file kept as text: `app/Resources/AppIcon.icon/` with `icon.json` and two SVG layers.
  - `scripts/build-icon.sh` compiles it with `xcrun actool` into a bundle's `Contents/Resources`, as `Assets.car` and `AppIcon.icns`, and `build-app.sh` calls it.
  - Without `actool` (the Command Line Tools only), it says so and the build goes on without the icon.
  - `tests/icon_test.sh`, in `make test`, checks each of its branches.
  - `Info.plist` names the icon with `CFBundleIconFile` and `CFBundleIconName`.

**Spec:** `docs/features/specs/2026-11-25-icon-and-name-design.md` ("the spec"; section numbers refer to it). Approved by the author on 2026-11-26, with this plan.

**Branch:** `icon-and-name`. It holds the spec's commits and the drawings.

## Execution notes

**A build is an install.** `scripts/build-app.sh` builds, signs and installs into `~/Applications`, and quits the running Shepit. So nothing before the gate uses it:
- **Task 1:** the menu bar is seen with `app/.build/debug/Shepit menubar-test`, after `swift build`. It adds a status item of its own for a few seconds and leaves the running Shepit alone.
- **Task 2:** `scripts/build-icon.sh` writes into a test bundle in the scratchpad. There, the icon macOS shows is rendered with `NSWorkspace` (spec §5), Quick Look shows `AppIcon.icns`, and an ad hoc signature (`codesign --sign -`, no certificate) passes `codesign --verify --strict`.

**What `actool` does when it fails** (tried on 2026-11-26, Xcode 26.6):
- an `icon.json` it can't read: exit 1, with the error on stderr and in its stdout's plist;
- an `--app-icon` name that isn't the `.icon` folder's name: exit 0, and nothing written.

`build/Shepit.app` is never cleaned, so the script removes the old icon before compiling and then checks that `AppIcon.icns` was written.

**Without `actool`:** `DEVELOPER_DIR=/Library/Developer/CommandLineTools xcrun --find actool` fails on this Mac, which has both. That is how the test reaches the branch without Xcode.

**Task 2 is risky.** Every install goes through `build-app.sh`. Its reviewer reads `scripts/install.sh` and `tests/install_test.sh` too.

**One gate,** Task 3: one install, after both tasks, as each install may stop a running transcript. Claude asks first.

**No test data.** Nothing here reads or writes settings, databases or the author's files.

## Global constraints

- **The bundle id and the signing certificate stay**, so the Accessibility, Microphone and System Audio Recording grants stay. The icon is written into the bundle before `codesign`, which signs it.
- **The Command Line Tools alone still build Shepit**, as the README promises (spec §5).
- **No new setting, no network, no new permission.**
- **The menu itself doesn't change**, nor do the panels' 🔴 and ⏳, nor the menu's ⚠ and ⏺ lines (spec §3).

## Review focus

1. **`build-icon.sh`** (Task 2):
   - without `actool` it warns, writes nothing, and the build goes on;
   - when `actool` fails, or writes no `AppIcon.icns`, it fails before anything is installed, also when an older build left an icon there;
   - `codesign --verify --strict` passes with the new resources.
2. **`MenuModel.icon` keeps every case of today's title** (Task 1):
   - the problem mark only while idle, from a failed load or a taken hotkey;
   - the meeting's dot while a transcript records, finishes or detects speakers, and not when it is idle, done or interrupted.
3. **The drawn image** (Task 1):
   - it may be drawn off the main thread: the drawing is `nonisolated` and captures only the icon;
   - a template exactly when plain;
   - colours that follow a light, a dark and a tinted menu bar, also with Shepit's theme set against the system's (`applyTheme` sets `NSApp.appearance`);
   - no new image every second: both paths go through one `show(_:)`.
4. **VoiceOver and the tooltip** (Task 1): the button has no title now, so it gets a label of its own.

### Task 1: The rhombus in the menu bar (spec §6)

- **Probe first,** before the code. A small status item draws a non-template rhombus with `labelColor` in its drawing handler, in the scratchpad. It is drawn with `NSApp.appearance` unset, then set to `aqua` and to `darkAqua`, on this Mac's menu bar.
  - **If `labelColor` follows the menu bar each time,** the task goes as written.
  - **If not,** the rhombus stays a template in every state. Then:
    - recording tints it red with the button's `contentTintColor`;
    - transcribing fades it with the button's `alphaValue`;
    - the two dots are a second, coloured image in the button's title, beside it.

    Spec §6's "My calls" line changes to say so, before the code.
- **Tests first,** in `MenuModelTests`:
  - **`titleReflectsStateAndProblems` becomes `iconReflectsStateAndProblems`:**
    - ready;
    - `.problem` from `load = .failed` and from `hotkeyProblem`;
    - `.recording`, also with `hotkeyProblem` set, as the problem shows only while idle;
    - `.transcribing` with `load = .loading`.

    None of these has the meeting's dot.
  - **`meetingMarkInTheTitleWhileASessionRuns` becomes `meetingDotWhileASessionRuns`:**
    - `recording`, `finishing` and `detectingSpeakers` give the dot;
    - `idle`, `done` and `interrupted` don't;
    - with the dot, the dictation's mark is as it is: `.recording` while a dictation records, and `.problem` with a taken hotkey.
  - **New: `onlyReadyAndTranscribingWithoutAMeetingArePlain`,** a loop over all eight icons (`Mark.allCases` × the meeting).
- **The change in ShepitCore** (`MenuModel.swift`):
  ```swift
  /// The menu bar's rhombus (icon and name design §6): the dictation's mark, and a dot while a meeting transcript runs.
  public struct MenuIcon: Hashable, Sendable {
      public enum Mark: CaseIterable, Sendable { case ready, recording, transcribing, problem }
      public var mark: Mark
      public var meeting: Bool
      public init(mark: Mark, meeting: Bool) { self.mark = mark; self.meeting = meeting }
      /// No colour: drawn as a template, which macOS tints for any menu bar.
      public var isPlain: Bool { !meeting && (mark == .ready || mark == .transcribing) }
  }
  ```
  `icon(_:)` replaces `title(_:)` and `dictationTitle(_:)`, with today's rules.
- **The change in the app** (`MenuController.swift`):
  - **Renames.** `refreshTitle()` becomes `refreshIcon()`, and the init's `title:` closure becomes `icon:`. Their callers are `AppHost.swift` and `AppHost+Window.swift`.
  - **`private func show(_ view: AppSnapshot)`** is used by both `refreshIcon()` and `menuNeedsUpdate`. A `shown: MenuIcon?` holds the last icon, and the image is set only when the icon differs. The tooltip ("Shepit: " and the status line) is set each time, and so is the button's accessibility label, to the same text.
  - **`nonisolated static func image(_ icon: MenuIcon) -> NSImage`**, with `NSImage(size:flipped:drawingHandler:)`.
    - **The handler captures only `icon`.** AppKit may call it on any thread. A handler written inside the `@MainActor` class traps there; the critic saw it trap.
    - **The rhombus:** the 10 rects of the round 3 glyph (`gR` in the drawings), in 7 columns, in 18×18 pt, each 1.6 wide with corners of 0.4:

      | x | y, height |
      |---|---|
      | 0.9 | 7.8, 2.4 |
      | 3.3 | 5.3, 7.4 |
      | 5.8 | 3, 5.6 and 9.4, 5.6 |
      | 8.2 | 0.5, 5.6 and 11.9, 5.6 |
      | 10.6 | 3, 5.6 and 9.4, 5.6 |
      | 13.1 | 5.3, 7.4 |
      | 15.5 | 7.8, 2.4 |

    - **Its colour:**
      - ready and a problem: `labelColor`;
      - recording: `systemRed`;
      - transcribing: `labelColor` at 40%.
    - **A problem:** a `systemOrange` dot of 5 pt at the top right, with 1 pt cleared around it, so it doesn't touch the bar beside it.
    - **A meeting:** a 6 pt `systemRed` dot, centred on the left, and 3 pt of space before the rhombus. The image is 27 pt wide.
    - **`isTemplate = icon.isPlain`.**
- **`Shepit menubar-test [light|dark]`** (`main.swift`, and `MenuBarTest` beside `MenuController`):
  - like `CallPanelTest`, it shows each of the eight icons in a status item of its own for 2 s, printing its name, then quits;
  - `light` or `dark` sets `NSApp.appearance` as Shepit's theme does.
- **Test** in `app/Tests/ShepitTests/MenuControllerTests.swift`: every one of the eight images is drawn into a bitmap from a background queue. Each has a pixel that isn't clear, is 18 pt high, and is 18 pt wide, or 27 with a meeting.
- `make test` green. Claude runs `menubar-test` three times, with no theme, `light` and `dark`, and the author looks at it in their menu bar. Their remarks are fixed in this task.
- Commit `Shepit: the rhombus in the menu bar, in every state`.

### Task 2: The app icon (spec §5) (risky)

- **The files.** `app/Resources/AppIcon.icon/` from the one tried on 2026-11-26 (scratchpad `icon/B2.icon`):
  - `icon.json`: the linen's gradient (#f7f2e8 to #e6dcc8) as the fill. One group holds the stitches, with a neutral shadow at 0.5 and no translucency; the other holds the weave, with no glass. It is for macOS only.
  - `Assets/stitches.svg` and `Assets/weave.svg`: B2 on the 1024 canvas, scaled up from its 824 body, as the system draws the shape.
- **`Info.plist`:** `CFBundleIconFile` and `CFBundleIconName`, both `AppIcon`.
- **Tests first:** `tests/icon_test.sh`, run by `make test` after the installer's test, in a temporary folder:
  - **it compiles:** a copy of `AppIcon.icon` writes `AppIcon.icns` and `Assets.car`;
  - **a broken `icon.json`:** the script fails;
  - **a folder named `Other.icon`, after a good run into the same folder:** the script fails, as the old `AppIcon.icns` is gone;
  - **with `DEVELOPER_DIR=/Library/Developer/CommandLineTools`:** the script says it has no `actool`, exits 0, and the folder has no icon. This case is skipped when that folder doesn't exist.

  The first three are skipped, with a line saying so, when there is no `actool`.
- **`scripts/build-icon.sh <the .icon folder> <a Contents/Resources folder>`,** with a comment pointing to spec §5:
  ```bash
  set -euo pipefail
  REPO="$(cd "$(dirname "$0")/.." && pwd)"
  icon="$1" resources="$2"
  mkdir -p "$resources"
  rm -f "$resources/Assets.car" "$resources/AppIcon.icns"
  if ! xcrun --find actool >/dev/null 2>&1; then
      echo "No actool (it comes with Xcode): Shepit is built without its icon" >&2
      exit 0
  fi
  partial="$(mktemp -d)"
  trap '/bin/rm -rf "$partial"' EXIT
  # --app-icon must be the .icon folder's name, or actool writes nothing and still exits 0.
  if ! out="$(xcrun actool "$icon" --compile "$resources" --platform macosx --app-icon AppIcon \
      --minimum-deployment-target "$(plutil -extract LSMinimumSystemVersion raw "$REPO/app/Resources/Info.plist")" \
      --output-partial-info-plist "$partial/AppIcon.plist" 2>&1)"; then
      echo "$out" >&2; exit 1
  fi
  [[ -f "$resources/AppIcon.icns" ]] || { echo "actool wrote no AppIcon.icns from $icon" >&2; exit 1; }
  ```
  The partial plist isn't merged, as `Info.plist` carries the same keys.
- **`build-app.sh`:** after `Info.plist` is copied, `"$REPO/scripts/build-icon.sh" "$REPO/app/Resources/AppIcon.icon" "$APP_BUNDLE/Contents/Resources"`.
- **Checked before the gate,** in a test bundle in the scratchpad (Execution notes):
  - `NSWorkspace` shows B2 filling the shape;
  - Quick Look shows `AppIcon.icns` (spec §9, check 6);
  - an ad hoc signature passes `codesign --verify --strict`.
- `make test` green. Commit `Shepit: the app icon, B2, compiled from an Icon Composer file`.
