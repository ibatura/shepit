# Native app — App shell, build, signing, install

Part of the native app design; see `00-overview.md`.

## 1. The app

- `Shepit.app`, a menu-bar-only app (`LSUIElement`, no Dock icon). Written in
  Swift (AppKit and SwiftUI as fits; the overlay panel needs AppKit `NSPanel`).
- Minimum macOS 14.2 (needed for the process tap in phase 3; keeping one minimum
  avoids two code paths). Apple Silicon only.
- The bundle identifier is chosen once and never changed: macOS keys permissions to
  it and to the signing identity. *(My call: exact identifier left to the builder.)*
- **Launch at login** through `SMAppService.mainApp`, setting `launchAtLogin`
  (default `true`), shown in Settings → General.
- Single instance: a second launch activates the first one's Settings window and exits.
- The menu-bar icon and the menu keep today's meaning and items (see
  `03-dictation.md` §7).
- A command-line mode for tools: `Shepit.app/Contents/MacOS/Shepit bench …`
  (see `02-engines.md` §6). It runs without the menu-bar UI and exits.

## 2. Permissions

The app asks for its own permissions under its own name:

| permission | why | when asked |
|---|---|---|
| Microphone | recording | first dictation (Info.plist `NSMicrophoneUsageDescription`) |
| Accessibility | sending ⌘V to paste and ⌘C to read a selected word | first launch: the app explains and opens the System Settings pane |
| Screen & System Audio Recording | process tap for meetings (phase 3) | first meeting start (`NSAudioCaptureUsageDescription`) |
| Speech Recognition | only if the Apple engine needs it (`NSSpeechRecognitionUsageDescription`); verify in phase 1 | first use of the Apple engine |

The global hotkeys use Carbon `RegisterEventHotKey` (press and release events),
which does not need Accessibility. If Accessibility is missing, dictation still
works and the text is copied to the clipboard and saved to history, and a notice
says why it wasn't pasted (today the paste silently fails).

## 3. Code signing

**Why:** macOS remembers permissions by the app's signature. With no signature or an
ad-hoc one, every rebuild looks like a new app and Accessibility has to be granted
again. A stable signing identity avoids that.

**What the build script does** (`scripts/build-app.sh`), in this order:
1. If `DICTATION_SIGN_IDENTITY` is set, use it.
2. Else, if the login Keychain has an **Apple Development** identity, use it (people
   with Xcode signed in to an Apple ID).
3. Else use, creating it if missing, a **self-signed code-signing certificate**
   named `Shepit Local Signing`, valid 10 years, in the login Keychain, trusted
   for code signing. Creating and trusting it asks for the user's login password
   once; the script says so before it happens.

Each person who builds gets their own certificate; nothing is shared or committed.
A locally built app has no quarantine flag, so Gatekeeper doesn't block it.

No App Sandbox and no hardened runtime (not needed without notarization), so no
special entitlements. The script verifies the result (`codesign --verify`) and prints
which identity it used.

**Phase 1 gate:** before building anything else, verify on this Mac that with the
self-signed identity, Accessibility and Microphone stay granted across two rebuilds
and reinstalls. If they don't, stop and report to the user.

**Later (non-goal now):** Developer ID + notarization to hand out a prebuilt app.
Only the signing step and a notarization step change; the code doesn't.

The README gets a "Code signing" section: what happens on the first build (password
prompt), how to check the signature, how to use your own identity, and what to do
if permissions were lost (remove the app from the Accessibility list and add it again).

## 4. Build

- Dependencies through Swift Package Manager, each **pinned to an exact version or
  commit** with the resolved file committed: WhisperKit, FluidAudio, whisper.cpp
  (its Swift package / XCFramework, built with Metal).
- Builds from the command line with one script (`scripts/build-app.sh`); no manual
  steps in the Xcode IDE. How the project is described (Xcode project generated by
  a tool such as XcodeGen, or SwiftPM plus a bundle-assembly step) is left to the
  builder, as long as the generated project is reproducible from committed files.
- Requirement for builders: Apple Silicon Mac, macOS 14.2+, Xcode, and `cmake`
  (whisper.cpp has no Swift package, so it is built with cmake into a static
  library). Whether the Command Line Tools alone are enough is checked in phase 1;
  the README states the result. *(My call, found while planning.)*
- Like `build-whisper.sh`, the script skips the build if a stamp of the sources and
  resolved dependencies is unchanged, and installs by copy-then-rename.
- `scripts/build-whisper.sh` and `patches/whisper-server-auth.patch` are no longer
  needed after the switchover (no server) and are removed then.

## 5. Install, uninstall, files

- `scripts/install.sh` (after switchover): checks Xcode, builds and signs the app,
  installs it to `~/Applications/Shepit.app` *(my call: no admin rights needed)*,
  downloads models (`02-engines.md` §5), creates `settings.json` and
  `dictionary.json` from `examples/` if absent (never overwrites), removes the
  Hammerspoon loader block if present, and opens the app. Safe to run again.
  Homebrew is needed only for `cmake` (any other cmake install works too).
- `scripts/uninstall.sh`: quits the app, removes it and its login item; keeps
  settings, dictionary, history, statistics and models unless `--purge`.
  `--purge` deletes `~/.config/dictation` and `~/.local/share/dictation` (which
  includes the default meetings folder, never a custom one).
- `tests/install_test.sh` is updated to the new scripts and stays green.

| what | where |
|---|---|
| App | `~/Applications/Shepit.app` |
| Settings, dictionary | `~/.config/dictation/settings.json`, `dictionary.json` (unchanged) |
| History | `~/.local/share/dictation/history.log` (unchanged format) |
| Failed audio | `~/.local/share/dictation/failed/` (unchanged) |
| Statistics | `~/.local/share/dictation/stats.sqlite` |
| Models | `~/.local/share/dictation/models/` (existing ggml files stay; new engines in subfolders) |

## 6. Switchover from the Lua tool

- During phases 1–2 the native app is built with `scripts/build-app.sh` and started
  by hand. The Lua tool keeps working. Running both at once would fight over the
  hotkeys, so the native app does not register hotkeys while the Hammerspoon
  tool's hotkey is taken; it shows "Hotkey taken" in its menu. The user quits
  dictation in the 🎙 menu to try the native one.
- When dictation parity is reached and the user agrees, `install.sh` switches over
  (removes the Hammerspoon block). Hammerspoon itself is left installed.
- The Lua code (`src/`, `tests/*.lua`, `Makefile` targets) is deleted from the repo in
  a separate commit after the user has used the native app for a while and says so.
  Git history keeps it.
- The README is rewritten for the native app at switchover.
