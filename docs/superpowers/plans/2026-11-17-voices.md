# Main window, part 5 (Voices and People): implementation plan

**Goal:** Shepit remembers voices while Remember voices is on: a voice sample per transcript line, a print per person made from the lines that are theirs now, recognition when a transcript is ready, and the People section with everyone named, their voice, meetings and talk time, rename, merge, delete, suggestions for earlier meetings and the author's own voice.

**Architecture:** A person is a row of `persons` in `meetings.sqlite` (version 2 through `SQLiteFile`'s numbered upgrades); a meeting's Person N links to one. Samples are rows of `samples`, keyed like `lines`; a print is never stored, it is the samples of the lines a person has now, so every correction already in the store (name, merge, give, reset) changes it. Everything that decides is pure and unit-tested in `ShepitCore` (`VoiceSample`, `Voices`, `PeoplePage`, `MeetingStore`); `ShepitEngines`' `Diarizer` also returns window embeddings; the app gets `PeopleModel` / `PeopleView`, recognition in `AppHost+Meetings`, and `Shepit voices-check`.

**Spec:** `docs/superpowers/specs/2026-11-17-voices-design.md` ("the spec"; section numbers refer to it). Look: `docs/superpowers/specs/2026-11-11-visual-style/` (`visual-style.md` §5.2, §5.5; `mockups.html` screens 2 and 6). Builds on `2026-11-14-meetings-design.md` ("the meetings spec").

**Branch:** `voices`, cut from `main`. When it is ready: push it and open a pull request with a description, merged as one squashed commit; while `gh` is not logged in, merge it into `main` locally. Ask the author before merging either way.

## Execution notes

- **Style: Ponytail (full)** for every task (`~/.claude/skills/ponytail`): the smallest complete change, a test for every non-trivial branch, no options nobody asked for.
- **Review per task:** the task's diff is checked against the Ponytail rules; Tasks 1, 3 and 5 also get `/code-review` on their diff (the upgrade, recognition, changes across many notes).
- **Review at the end (Task 10):** the author runs `/thermo-nuclear-code-quality-review` on the branch (only the author can start it); then `/code-review` and `/security-review` on the whole branch. Findings are shown to the author as a list; the author picks what to change.
- One task at a time, a commit per task with a short message, `make test` green after each (569 tests on 2026-11-17).
- Tests first for everything in `ShepitCore`. Tests use databases and notes in temporary folders, never `~/.local/share/dictation` or the author's meetings folder.
- The author's own `~/.config/dictation/settings.json` is not changed by code or tests; Remember voices is turned on by the author, in the People section.
- **Call content is confidential.** On the author's real meetings and `meetings.sqlite`: counts and rates only, people as "person 1, 2…", no names, no transcript text.
- Don't install (it restarts Shepit) while a transcript may be running: ask first.
- From Task 4 on, look at each view next to mockups 2 and 6 (light and dark) before the commit; a scratch render test (an `NSHostingView` in a window, cached to a PNG in the scratchpad, deleted before the commit) is the quick way.
- **Author gates: Task 2 (a real meeting with Remember voices on), Task 4 (the People section) and Task 10.**

## Global constraints

- **Biometric data:** samples are written only while `rememberVoices` is on, only to `meetings.sqlite` in `databasesFolder`, never to `stats.sqlite`, logs or the scratchpad. Every way out deletes them: Remove note from list, Move file to Trash, Delete voice, Delete all voices, and 30 days for a person with no name.
- No audio kept: samples are taken before `cleanUpAudio()` deletes the session folder, `mic.wav` included.
- Every change to people writes the database and every note it touches together, or none of them (meetings spec §8); a note is written through a temp file and a rename, headers only.
- An upgrade of an older `meetings.sqlite` keeps every meeting, line and name; a failed upgrade changes nothing and is tried again on the next open.
- Recognition never takes a name the author gave: it only links a Person N with no person, and marks it.
- Stop stays quick: the time speaker detection, samples and recognition add is measured in Task 2 and Task 8 and reported to the author.
- No network, no new permission. One new setting, `rememberVoices` (default `false`), validated like the others and listed in `examples/settings.json`. Window state (the People period, the chosen person) in `UserDefaults`.
- Standard SwiftUI controls and SF Symbols; English labels in sentence case; texts as in the spec and the mockups.

## Review focus

1. **Privacy:** nothing written with Remember voices off; every deletion path really deletes the samples; no names in `stats.sqlite`; `voices-check` prints no names or text. Tasks 2, 3, 4, 7.
2. **The upgrade is safe:** a version-1 file keeps its meetings, lines and names; names the same ignoring case, accents and script become one person; the author's labels become You. Task 1.
3. **Changes across notes are atomic:** rename and merge across many meetings leave every note and the database as they were when one note can't be written; a missing note changes only the database. Task 5.
4. **Recognition is careful:** threshold and margin, one person per meeting, never over a given name, marked "recognised by voice", undone by the usual means. Task 3.
5. **Prints follow corrections:** naming, merge, give a line, new person, reset, delete a meeting, delete a voice: each changes which samples a print has, and nothing else needs updating. Task 3.
6. **Cost:** the time added after Stop; one read of samples per recognition and per People reload, not per redraw. Tasks 2, 3, 4.

### Task 3: Prints, recognition and voices-check

- [ ] Tests first for `Voices`:
  - `prints(_ rows: [(person, meeting, sample)])`: one print per person, the mean of its samples (and its samples kept for the nearest-sample check).
  - `recognise(meeting people: [key: [sample]], prints:, threshold:, margin:)`: links a Person N whose best match passes the threshold and leads the second best by the margin; never two keys to one person (the closer wins); a person whose only samples come from this meeting is not used; You can match.
  - A print follows the store: naming, merge, give a line, new person, reset, removing a meeting (store-level tests on a temporary file).
- [ ] `MeetingStore.printRows()` (samples joined with lines and people, grouped by person, only linked people) and `MeetingStore.recognise(_ meeting:, links:)`: through `change` (the note's headers and the database together), only Person N rows with no person, `recognised = 1`; a You match merges that key into the meeting's you label. Changing the name, merging or resetting clears `recognised` (Reset keeps links, as names stay today).
- [ ] The 30-day deletion: samples of lines whose person has no link, in meetings started more than 30 days ago, at launch and after each added meeting. Test with a fixed now.
- [ ] `AppHost+Meetings`: after a transcript with samples is added, recognition with Remember voices on; the Transcript ready detail says "2 of 4 people recognised" (`CallOffer.readyDetail`, tested). The Meetings section shows "recognised by voice" under a recognised person's name.
- [ ] `Shepit voices-check` (`VoicesCheck.swift`, wired in `main.swift` like `call-watch`): for each person with samples in two or more meetings, leave one meeting out, and print for thresholds 0.30–0.80 how many of those meetings' people would be recognised, wrongly named or missed, for the mean and for the nearest sample. Counts and rates only. A test for the counting on made-up samples.
- [ ] Start from a similarity of 0.8 and a margin of 0.1, as constants with a comment pointing to `voices-check`: FluidAudio's default (`SpeakerManager.speakerThreshold` 0.65 as a cosine distance, a similarity of 0.35) is far too low, since on the first meeting kept with voices (2026-11-18) the author's voice heard through the call and another person's had means 0.76 alike.

### Task 5: Rename and merge across meetings

- [ ] Tests first for `MeetingStore`:
  - `rename(person:to:)`: the person's one name changes; every note where a line of theirs shows the name gets its headers rewritten; a name another person has throws a clash (the view asks).
  - `merge(person:into:)`: every `people` row of the person links to the other; in a meeting with both, this person's lines go to the other's key (as a meeting merge does); the person is deleted.
  - Atomic: with one of three notes unwritable, all three notes and the database stay as they were (notes written are put back from their old text, then the transaction rolls back). A missing note changes only the database. Changes made in Obsidian meanwhile stay (each note read right before writing).
- [ ] People: the editable title (saved on Enter or when focus leaves, empty puts the old name back); a taken name asks "Marko D. is already in People. Merge Olena into Marko D.?" with Merge, Keep both and Cancel; Merge into… with the other people (not You as a source). A note that can't be written shows its path and the error, and nothing changes.
