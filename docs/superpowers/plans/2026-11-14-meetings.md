# Main window, part 2 (Meetings): implementation plan

**Goal:** The Meetings section of the window: a list of every transcript, a finished meeting with its people and its read-only transcript, and the meeting being recorded. People are named, merged and given single lines; the meeting is renamed; Reset people undoes it all. A local database (`meetings.sqlite`) keeps the list and who said each line. The menu keeps only Start and Stop for meetings.

**Architecture:** Reading and changing a note, the database and what the window shows are built in `ShepitCore` and unit-tested: a note parser and header writer on top of `MeetingNote` and `Speakers`, a `MeetingStore` over SQLite like `StatsDatabase`, and pure builders that turn the store plus a note into list rows, people rows and transcript rows, and a change into new note text plus a store update. `Shepit` gets `MeetingsSection` and the wiring in `AppHost+Meetings`.

**Spec:** `docs/superpowers/specs/2026-11-14-meetings-design.md` ("the spec"; section numbers refer to it). Look: `docs/superpowers/specs/2026-11-11-visual-style/` (`visual-style.md` §5.2; `mockups.html` screens 2 and 3).

**Branch:** `meetings`, cut from `main`. Ask the author before merging into `main` and before pushing.

- **Author gates: Task 6 (the screens) and Task 9.**

## Global constraints

- The note is the transcript; the database never holds its text.
- The window changes only entry header labels and the front matter `title` line, always reading the note right before and writing through a temp file and a rename.
- A change lands in the note and the database together or in neither.
- No folder is listed or scanned. The list checks that each note exists; a note is read only when its meeting is opened.
- Nothing runs for Meetings while the window is closed, apart from adding a finished transcript.
- Standard SwiftUI controls and SF Symbols; English labels in sentence case; texts as in the spec and the mockups.
- No network, no new permission, no new setting.

## Review focus

1. **The author's notes are safe:** only headers and the `title` line change; hand edits to text survive every window change; a second with entries added or deleted in Obsidian is left alone (spec §8). Tasks 1 and 3.
2. **Note and database agree:** every change either reaches both or neither, including a failed write and a note edited between the read and the write. Tasks 2, 3 and 7.
3. **Privacy:** no transcript text in `meetings.sqlite`; no scanning; nothing new leaves `~/.local/share/dictation` or the meetings folder.
4. **Idle and live cost:** nothing for Meetings while the window is closed; the live view reads the session's memory, not the note, once a second. Tasks 5 and 6.
5. **Nothing is lost from the menu:** each removed item has its place in the window (spec §9).

### Task 1: Reading and changing a note

- [ ] Tests first: `MeetingNote.parse(note)` gives the front matter's `date`, `time`, `title`, `app` (each optional; the quoted and escaped title of `frontMatter` read back) and the entries in order, each with label, timestamp, text (the lines up to the next header, joined, the leading backslash escape removed) and its header's line number; ⚠ lines are entries of their own kind with no label; CRLF endings; a note with no front matter; a note with no headers gives no entries.
- [ ] Tests first: setting the labels of chosen entries (by index) changes only those header lines and keeps CR, text and every other line byte for byte; a label with a newline is made one line (as `Speakers.rename`).
- [ ] Tests first: setting the `title` line replaces it, adds it after `time` when missing, removes it for no name, and leaves the rest of the front matter and the body untouched; a note without front matter is left as it is.
- [ ] `Speakers.relabel` keeps its behaviour and tests; shared header code moves where both use it.
- [ ] Commit `Shepit: read meeting notes and change single headers`.

### Task 2: The meetings database

- [ ] Tests first for `MeetingStore` on a temporary file:
  - A new file gets the schema and a version; reopening keeps the data.
  - `add(note:start:duration:title:app:you:entries:)` stores the meeting, one person per distinct label (in order of first line) and one line per labelled entry (timestamp, order in its second, original and current person); returns the meeting's id. Adding a path that is already listed does nothing and says so.
  - `meetings()` newest first with path, name, app, start, duration.
  - `rename(id, title)`, `relink(id, path)`, `remove(id)` (people and lines go too).
  - Person and line changes: name a person; give a line to a person; merge (all current lines of one person to another); new person (the next free "Person N"); reset (every current person back to the original). Each in one transaction.
  - `suggestedNames(excluding: id)`: names given to people in other meetings, newest meeting first, without duplicates, without empty names and labels.
  - A failure inside a transaction leaves the database as it was.
- [ ] Open lazily, as `StatsDatabase` does; the file is `Paths.dataDir/meetings.sqlite` (a `Paths` entry, with its test).
- [ ] Commit `Shepit: meetings database`.

### Task 3: The meeting as data

- [ ] Tests first for pairing (spec §8): the k-th entry with timestamp T is the k-th stored line with T; a second whose counts differ is unpaired on both sides; ⚠ entries are never paired.
- [ ] Tests first for the page of one meeting: people rows (stored people with current lines, order of first line, label or name, initials, "you", share of words without ⚠ lines and failed chunks); transcript rows (shown name, time, text, paired or not); Reset off when nothing differs; the merge targets of a person (others, "you" included) and of "you" (none).
- [ ] Tests first for changes: each of name, merge, give, new person, reset gives the new note text (only the headers of the lines that change, read from the current note) and the store operation; a person's name that another person of the meeting has is reported as a merge question, not applied; an empty name puts the label back.
- [ ] Tests first for the list: groups This week, Last week, then months, by the calendar's first weekday; row title (name, "Teams call", "Meeting"), detail ("Tue 10:00 · 48 min · Teams", "3 Oct, 10:00 · …", "· note not found"); the running row for recording, finishing and detecting.
- [ ] Commit `Shepit: meetings list and meeting page as data`.

### Task 4: Renaming a meeting

- [ ] Tests first: the new file name is the last part of `MeetingFileName.relativePath` with the new name, start and app, in the note's current folder, made unique against other files (the note itself doesn't count as taken); a template without `{title}` keeps the name; a template with folders still renames in place; an empty name gives the name without a title.
- [ ] Tests first: `MeetingNames` renames the entry with a given start, adds one when there was none, removes it for an empty name.
- [ ] One function puts a rename together: new note text (Task 1's title line), the new path, the store's `rename` and `relink`; for a missing note only the store and the names file.
- [ ] Commit `Shepit: rename a meeting and its note`.

### Task 5: The app keeps the list

- [ ] `AppHost` owns one `MeetingStore`. A meeting is added when a transcript is ready (not when the empty one is removed), when Shepit quits during one (after `interrupt()`), and at launch after a crash (`MeetingSession.recover` returns the note); spec §4 gives what each passes.
- [ ] `MeetingSession`: public words so far and the entries it wrote (label, time, text) for the live view; `last-meeting` no longer written, and `removeEmptyNote` loses the restore; the leftover file is deleted in `recover`. Tests for both, and the existing tests updated.
- [ ] The app of a meeting is a `CallApp?` from `MeetingTitle.detect` through `startMeeting`, `MeetingConfig` and `AppSnapshot` to the store; `settings.json` strings stay. Tests updated.
- [ ] Menu: Copy last meeting transcript, Rename speakers…, Rename speakers in another note… and Open meetings folder removed, with their `AppAction` cases and the rename dialogs; `MenuModelTests` say they are gone. Open meetings folder stays as an action for the window.
- [ ] Install; a short transcript (a call to yourself or `afplay` of a clip) appears in `meetings.sqlite` with its lines (check counts with `sqlite3`, not texts).
